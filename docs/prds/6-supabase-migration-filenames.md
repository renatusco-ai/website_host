# PRD 6 — Regenerate Supabase migration filenames

## Problem statement

The intake migrations in `website_host/supabase/migrations` use sequential prefixes. Renatus wants future migrations and existing migrations that can safely be renamed to use the timestamp format generated by the Supabase CLI. Supabase uses the filename prefix as the migration version, so renaming a recorded version can make it appear pending again.

## Solution

Generate distinct UTC timestamp prefixes for eligible migrations. Preserve the descriptive suffixes, SQL contents, and execution order. Use the Supabase CLI to generate names for new migrations.

## Migration filename mapping

| Previous filename | Timestamped filename | Purpose |
| --- | --- | --- |
| `001_app_store_intakes.sql` | `20261126021631_app_store_intakes.sql` | Creates the initial intake schema and private asset bucket. |
| `002_quick_app_store_intake.sql` | `20261126021633_quick_app_store_intake.sql` | Updates the intake schema for the shorter client form. |
| `003_intake_storage_names.sql` | `20261126021635_intake_storage_names.sql` | Renames intake database and storage objects. |

On 26 November 2026, the `renatus_schema` Supabase project configured for the intake reported only its main branch. A read-only check found no matching versions or statements in its migration ledger and no intake tables, RPCs, or buckets in the deployed schema. The three files were renamed in order and compared byte for byte.

The timestamped chain passed on a fresh local Supabase database, including private bucket provisioning. The production dry run from `website_host` returned `DbPushMissingLocalError` because that project has 119 other migration versions absent from this checkout. Repeating the dry run from a disposable workspace with the 119 production migrations listed only the three timestamped intake migrations as pending.

## Implementation decisions

1. Compare the local migration versions with the history of each deployed Supabase environment. Verify whether any of the SQL was applied manually, since manually executed SQL may be absent from migration history.
2. Rename versions confirmed unapplied everywhere to `YYYYMMDDHHMMSS_<existing_name>.sql`, using unique timestamps that sort in the order above. If a migration must keep its existing version, preserve ordering across the entire chain. Leave any rename pending when its applied status is unknown.
3. Keep recorded historical versions under their existing filenames by default. If those filenames must also change, prepare a separate migration-history reconciliation for each affected environment. Verify schema state and test the reconciliation on a disposable copy before touching deployed history. Record the old-to-new mapping so the history can be restored without rerunning SQL.
4. Update active setup instructions and scripts that reference a renamed file. Record the final mapping and document `supabase migration new <name>` for future migrations.

## Verification and acceptance criteria

- Every eligible file has a unique timestamped filename and retains its original suffix. The mapping accounts for all three files and identifies any versions that stay in place.
- Compare the old and new files byte for byte. The migration chain preserves the order `001 → 002 → 003`, with the new versions substituted where applicable.
- Apply the chain to a fresh disposable local database and confirm that the expected intake schema and private storage bucket are available.
- Check migration history and run a dry run against the intended linked environment before rollout. SQL that already ran must never appear in the deployment plan as pending work.
- Confirm that setup references point to the correct files and that future migrations use CLI-generated names.

## Out of scope

Schema and data changes, migration squashing, and production migration-history changes as part of drafting this PRD.
